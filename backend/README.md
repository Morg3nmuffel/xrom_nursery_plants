# Backend питомника

Учёт растений, задачи сотрудников и склад расходников работают как три отдельных HTTP-сервиса. При регистрации посадки сервис учёта создаёт партию и событие в одной транзакции. Планировщик находит партию в общей базе растений и назначает задачу одному из пяти сотрудников. Склад получает событие по HTTP и списывает материалы по норме посадки в своей базе.

## Запуск трёх сервисов

Понадобится Node.js 24.4 или новее. Скопируйте [шаблон](examples/demo.env.example) в `examples/demo.env` и задайте непустые `ADMIN_PASSWORD`, `POS_TOKEN` и `MATERIAL_SYNC_TOKEN`. Выполняйте команды из папки, где рядом лежат `server.mjs`, `tasks` и `consumables`. Для локального примера подготовьте пять партий, учебные остатки расходников и норму посадки.

```sh
node --env-file=examples/demo.env server.mjs seed-demo
node --env-file=examples/demo.env consumables/server.mjs seed-demo
```

Откройте три терминала в этой же папке и выполните по одной команде в каждом.

| Микросервис | Порт | Команда |
| --- | ---: | --- |
| Учёт растений и продажи | 8787 | `node --env-file=examples/demo.env server.mjs` |
| Задачи сотрудников | 8788 | `node --env-file=examples/demo.env tasks/server.mjs` |
| Склад расходников | 8789 | `node --env-file=examples/demo.env consumables/server.mjs` |

Каждый процесс отвечает на `GET /health` на своём порту. Для проверки рабочего цикла зарегистрируйте посадку через `POST /api/admin/plantings` на порту 8787. Задание появится в `GET /api/tasks?scope=team` на 8788, а результат списания — в `GET /api/admin/plantings` на 8789. Токен для каждого API получают на порту соответствующего сервиса. [API задач](tasks/README.md) · [API склада](consumables/README.md)

Для рабочего запуска задайте один и тот же абсолютный `INVENTORY_DB` в процессах учёта растений и задач. Складу укажите отдельный `MATERIALS_DB` и адрес учёта в `PLANT_SERVICE_URL` (по умолчанию `http://127.0.0.1:8787`). Если раньше вы явно задавали складу порт `8788`, обновите `MATERIALS_PORT` до `8789` для запуска вместе с задачами.

Учёту и складу нужен `ADMIN_PASSWORD` и одинаковый ключ обмена `MATERIAL_SYNC_TOKEN`. Учёту также нужен отдельный ключ кассы `POS_TOKEN`. Для задач задайте `TASKS_EMPLOYEES_FILE` с пятью рабочими учётными записями. Для подключения панели администратора передайте всем трём процессам одинаковые `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Порядок запуска веб-приложения описан в [инструкции к frontend](../frontend/README.md). Пути в `demo-data` приведены в примере конфигурации. [Шаблон локальных настроек](examples/demo.env.example)

Все проверки запускаются командой `node --test` из папки с `server.mjs`.

## Учёт растений

HTTP-сервис на Node.js со встроенной SQLite. Одна строка учёта соответствует партии одного растения в одном месте и на одной стадии. Один сорт может одновременно расти в нескольких теплицах. Касса списывает проданные экземпляры из готовых партий. Администратор видит текущие остатки и историю изменений.

### Запуск сервиса учёта отдельно

Откройте PowerShell и запустите сервис с учебными партиями из примера на фото.

```powershell
$env:INVENTORY_DB = Join-Path $env:LOCALAPPDATA 'XromGroup\inventory-demo.sqlite'
$env:ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', (Read-Host 'Пароль для admin' -AsSecureString)).Password
$env:POS_TOKEN = [System.Net.NetworkCredential]::new('', (Read-Host 'Отдельный секретный ключ кассы' -AsSecureString)).Password
node server.mjs seed-demo
node server.mjs
```

Сервис слушает `http://127.0.0.1:8787`. Для запуска с готовым файлом SQLite укажите его полный путь в `INVENTORY_DB`. Для рабочего учёта с новой базой укажите её путь и запустите `node server.mjs`. В новую базу автоматически загружаются 12 карточек ухода из [plants.json](catalog/plants.json). Количество и местоположение появляются при регистрации партий.

Команда `seed-demo` однократно вносит пять [учебных партий с фото](examples/photo-batches.json). Для гортензии, туи и лаванды она использует названия из справочника. Для клематиса и петунии добавляет названия с фото. В ответе API поле `care` для этих двух растений равно `null` до импорта их карточек.

## Вход администратора и просмотр остатков

Во втором окне PowerShell из той же папки войдите с паролем, заданным при запуске.

```powershell
$api = 'http://127.0.0.1:8787/api'
$jsonType = 'application/json; charset=utf-8'
$password = [System.Net.NetworkCredential]::new('', (Read-Host 'Пароль admin' -AsSecureString)).Password
$credentials = @{ username = 'admin'; password = $password } | ConvertTo-Json
$session = Invoke-RestMethod -Method Post -Uri "$api/admin/login" -ContentType $jsonType -Body $credentials
$admin = @{ Authorization = "Bearer $($session.access_token)" }
$inventory = Invoke-RestMethod -Uri "$api/admin/inventory" -Headers $admin
$inventory.items | Format-Table id,name,location,stage_label,quantity,version
```

Токен администратора действует восемь часов. После выхода или перезапуска сервиса потребуется новый вход. Постоянный ключ кассы `POS_TOKEN` даёт доступ к обработке оплаченных чеков. Для подключения по сети перед сервисом нужен HTTPS. Файл рабочей базы хранится вне каталога, который раздаёт витрина.

## Посадка новых растений

Зарегистрированные посадки автоматически передаются в подключённый складской сервис для списания материалов. Запуск обоих процессов и настройка норм описаны в [инструкции по расходникам](consumables/README.md).

После посадки администратор отправляет `POST /api/admin/plantings`. Обязательны `planting_id` (уникальный номер посадки), `plant_id` (артикул из справочника), `location` и положительное целое `quantity`. Для первого поступления нового сорта передайте новый артикул и его название в `plant_name`. Сервис добавит сорт и партию одной транзакцией. Карточку ухода позже можно загрузить через `import-catalog`.

В примере высаживают 40 экземпляров лаванды в теплице 1, ряд 2. После входа администратора выполните команду с [примером посадки](examples/planting.json).

```powershell
$body = Get-Content -Raw -Encoding UTF8 examples/planting.json
$planting = Invoke-RestMethod -Method Post -Uri "$api/admin/plantings" -Headers $admin -ContentType $jsonType -Body $body
$planting | Format-Table planting_id,batch_id,location,stage,quantity,planted_at
Invoke-RestMethod -Uri "$api/admin/inventory/$($planting.batch_id)/history" -Headers $admin
```

Каждая посадка создаёт отдельную партию со своим календарём. В демонстрационной базе после примера будет 340 экземпляров лаванды в двух партиях — 300 на укоренении и 40 на посеве. Касса сможет продавать новую партию, когда она перейдёт в стадию `ready`.

По умолчанию сервис ставит стадию `sowing` и записывает текущее время. Для черенков или саженцев можно указать `stage` со значением `rooting` или `growing`. При внесении посадки задним числом укажите `planted_at` в UTC, например `2026-11-20T09:00:00Z`. Поле `growth_plan` принимает календарь переходов после этой даты. В истории партии посадка имеет вид события `planting` с фактическим временем посадки и временем регистрации.

Для новой посадки клиент создаёт новый `planting_id`, например UUID. При потере ответа следует повторить исходное тело с тем же номером. При первой записи сервис вернёт `201` и `batch_id`, при повторе — `200`, тот же `batch_id` и `replayed: true`. Использование номера с другими данными вернёт `409 planting_conflict`.

## Обезличенный оплаченный чек

После подтверждения оплаты кассовая система отправляет `POST /api/pos/sales` с заголовком `Authorization: Bearer <POS_TOKEN>`. Идентификатор товара `plant_id` соответствует `id` из справочника. Для смешанного чека отправитель выбирает строки растений. Для чека без растений событие учёта не требуется. Достаточно идентификатора кассы, номера чека, статуса и количества по позициям.

```json
{
  "register_id": "demo-pos-01",
  "receipt_id": "demo-0001",
  "status": "paid",
  "items": [
    { "plant_id": "hydrangea-paniculata-limelight", "quantity": 2 },
    { "plant_id": "thuja-occidentalis-smaragd", "quantity": 1 }
  ]
}
```

Отправить [этот чек](examples/paid-receipt.json) можно из окна, где выполнен вход администратора.

```powershell
$posKey = [System.Net.NetworkCredential]::new('', (Read-Host 'Ключ кассы' -AsSecureString)).Password
$pos = @{ Authorization = "Bearer $posKey" }
$receipt = Get-Content -Raw -Encoding UTF8 examples/paid-receipt.json
$sale = Invoke-RestMethod -Method Post -Uri "$api/pos/sales" -Headers $pos -ContentType $jsonType -Body $receipt
$sale.movements | Format-Table plant_id,batch_id,location,sold,remaining_after_sale
(Invoke-RestMethod -Uri "$api/admin/inventory?stage=ready" -Headers $admin).items
```

При исходных остатках с фото останется 118 гортензий и 63 туи. Сервис выбирает партии в стадии `ready` по порядку регистрации и при необходимости распределяет списание между несколькими партиями. В ответе `movements` перечислены фактические места и количества списания.

| Ответ кассе | Результат |
|---|---|
| `201`, `replayed: false` | Чек и все его списания сохранены одной транзакцией. |
| `200`, `replayed: true` | Совпали касса, номер и состав ранее проведённого чека. Возвращены исходные списания. |
| `409 receipt_conflict` | Под этим номером у кассы уже есть чек с другим составом. |
| `409 insufficient_stock` | Готового количества недостаточно хотя бы по одной позиции. Весь чек откатан. В ошибке указаны `plant_id`, `requested` и `available`. |
| `422 unknown_plant` / `receipt_not_paid` | Требуется проверить привязку артикула или статус оплаты. |

При потере ответа или `503 database_busy` касса повторяет исходное событие с теми же `register_id` и `receipt_id`. Номер должен быть уникальным в пределах кассы. Если нумерация начинается заново в каждой смене, включите идентификатор смены в `receipt_id`.

## Рост и правки партий

В справочнике описаны условия ухода. Источниками перехода стадии служат осмотр сотрудником и заданный им календарь конкретной партии. Поддерживаются `sowing` (посев), `rooting` (укоренение), `growing` (доращивание) и `ready` (готово к продаже).

После осмотра отправьте `PATCH /api/admin/inventory/{id}` с текущей версией строки, например `{"version":1,"stage":"growing"}`. Таким же запросом можно исправить местоположение или количество. При устаревшей версии сервис вернёт `409 stale_version` и номер текущей версии. Повторно прочитайте партию перед правкой, чтобы учесть уже проведённые продажи.

Для автоматических переходов передайте `growth_plan` при создании или изменении партии. Ниже пример тела `PATCH` для укореняющейся лаванды. Даты иллюстрируют формат и задаются питомником.

```json
{
  "version": 1,
  "growth_plan": [
    { "stage": "growing", "due_at": "2027-03-15T08:00:00Z" },
    { "stage": "ready",   "due_at": "2027-05-10T08:00:00Z" }
  ]
}
```

Даты указываются в UTC. План содержит будущие стадии в порядке роста с возрастающими датами. Новый массив заменяет прежний план, пустой массив отменяет его. Ручная правка стадии снимает переходы до этой стадии включительно. Фоновая задача каждые 30 секунд применяет наступившие переходы. При запуске она обрабатывает накопившиеся за время простоя шаги до приёма запросов. Каждый переход фиксируется в истории со временем исполнения и запланированной датой.

## Контракт API

Запросы с телом используют `Content-Type: application/json`. Ответы и ошибки возвращаются в JSON. Ошибка содержит объект `error` с полями `code`, `message` и связанными с операцией данными.

| Метод и маршрут | Доступ | Назначение |
|---|---|---|
| `GET /health` | Открытый | Проверка доступности сервиса и SQLite |
| `POST /api/admin/login` | Логин и пароль | Поля `username`, `password`. Ответ содержит `access_token` |
| `POST /api/admin/logout` | Администратор | Завершить текущую сессию |
| `GET /api/admin/plants` | Администратор | Все растения справочника и условия ухода |
| `POST /api/admin/plantings` | Администратор | Зарегистрировать фактическую посадку и пополнить остатки новой партией |
| `GET /api/admin/inventory` | Администратор | Объект с `count` и массивом партий `items`. Фильтр `?stage=ready` принимает любой код стадии |
| `POST /api/admin/inventory` | Администратор | Создать партию. Обязательны `plant_id`, `location`, `stage`, `quantity`. Опционален `growth_plan` |
| `GET /api/admin/inventory/{id}` | Администратор | Партия, версия и календарь переходов |
| `PATCH /api/admin/inventory/{id}` | Администратор | Передать текущую `version` и изменяемые поля `location`, `stage`, `quantity`, `growth_plan` |
| `GET /api/admin/inventory/{id}/history` | Администратор | Посадки, поступления, правки, переходы и продажи по порядку записи. У посадки есть номер и фактическая дата, у продажи — идентификаторы кассы и чека |
| `POST /api/pos/sales` | Касса | Провести оплаченный чек |
| `GET /api/internal/plantings?after=0` | Склад с `MATERIAL_SYNC_TOKEN` | Получить до 100 новых посадок после указанного номера события |

## SQL и обслуживание

Таблицы `plants` и `plant_care` содержат справочные данные, `plant_batches` хранит текущее состояние, `growth_plan` — календарь. Таблицы `paid_receipts` и `batch_events` связывают изменения остатков с чеками. Базовая структура описана в [schema.sql](schema.sql).

При первом запуске обновлённого backend укажите прежний путь `INVENTORY_DB`. Сервис последовательно применит недостающие миграции. Версия 2 связывает посадку с партией, версия 3 публикует новые посадки для склада в той же транзакции, что и регистрацию. [Учёт посадок](migrations/002-plantings.sql) · [Журнал для склада](migrations/003-planting-feed.sql)

Этот запрос к представлению `inventory` выбирает четыре колонки из макета.

```sql
SELECT name AS "Растение", location AS "Где", stage_label AS "Стадия", quantity AS "Кол-во"
FROM inventory
ORDER BY id;
```

Для обновления справочника выполните `node server.mjs import-catalog путь/к/plants.json`. Импорт добавляет и обновляет карточки по стабильному `id` одной транзакцией с сохранением связей с партиями. Для проверки сервиса учёта выполните `node --test test/inventory.test.mjs`.

| Переменная окружения | Назначение и значение по умолчанию |
|---|---|
| `ADMIN_USERNAME` | Логин администратора, по умолчанию `admin` |
| `ADMIN_PASSWORD` | Пароль администратора, задаётся при запуске |
| `POS_TOKEN` | Отдельный секретный ключ для кассового API, задаётся при запуске |
| `MATERIAL_SYNC_TOKEN` | Для подключения склада укажите общий для двух сервисов ключ чтения журнала новых посадок |
| `INVENTORY_DB` | Путь к SQLite. По умолчанию `XromGroup/inventory.sqlite` в каталоге данных пользователя (`LOCALAPPDATA`, `XDG_DATA_HOME` или `~/.local/share`) |
| `INVENTORY_HOST`, `INVENTORY_PORT` | Адрес и порт HTTP, по умолчанию `127.0.0.1` и `8787` |
| `GROWTH_INTERVAL_MS` | Период проверки плана роста в миллисекундах, по умолчанию `30000` |
